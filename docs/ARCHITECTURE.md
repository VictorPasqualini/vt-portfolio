# Architecture

## Overview

Single-page Next.js (App Router) site, statically exported. No backend, no database, no CMS — all content is checked into the repo as TypeScript objects.

```
app/layout.tsx        <html>/<body>, ThemeProvider, site-wide metadata, the optional analytics tag;
                      renders <html className="dark"> so the default theme never flashes light
app/[locale]/page.tsx one page per language, prerendered for en and pt: per-locale metadata
                      (title, canonical, hreflang, Open Graph), the Person JSON-LD block, and the
                      sections in order — Nav, Hero, Experience, Projects, Skills, Education, Contact, Footer
app/page.tsx          "/" entry stub: detects a language and redirects to /en or /pt (noindex)
app/sitemap.ts        static sitemap.xml listing both locale URLs with their alternates
app/robots.ts         static robots.txt pointing at the sitemap
lib/site.ts           absolute site URL, locale list, social/contact URLs — the single source for
                      anything that has to be an absolute link
```

## Theme (dark/light)

`lib/theme-context.tsx` exposes a `ThemeProvider` and `useTheme()` hook:

- `theme: 'light' | 'dark'`, **defaults to `'dark'`** regardless of the OS/browser `prefers-color-scheme` — this is an explicit product decision, not an accident of following the system.
- On mount, checks `localStorage` (`vt-portfolio-theme`) for a stored choice and applies it if present; otherwise stays on the default.
- `setTheme`/`toggleTheme` update state, persist to `localStorage`, and toggle the `dark` class on `document.documentElement`.
- Colors are CSS variables (`--bg`, `--fg`, `--line`, `--soft`, `--accent`, RGB triplets) defined in `app/globals.css` under `:root` (light values) and `.dark` (dark values, which match the default). Tailwind exposes them as the `bg`/`fg`/`line`/`soft`/`accent` colors (`tailwind.config.ts`, `darkMode: 'class'`) so components use e.g. `bg-fg`, `text-fg/70`, `border-line/10` and get both themes for free — no `dark:` variant classes needed anywhere.
- `app/layout.tsx` server-renders `<html className="dark">` so static/SSR output already matches the default theme; `ThemeProvider` only needs to *change* the class when a visitor has stored `'light'`, not add it on first paint — avoiding a flash of the wrong theme.

## i18n

`lib/i18n-context.tsx` exposes a `LocaleProvider` and `useLocale()` hook:

- **The URL is the source of truth.** `/en` and `/pt` are separate prerendered pages (`app/[locale]/page.tsx` + `generateStaticParams`), and the provider receives that segment as `initialLocale`.
- `setLocale(locale)` navigates to the sibling URL *and* stores the choice in `localStorage` (`vt-portfolio-locale`), so the address bar, the content and the remembered preference never disagree. Landing on a locale URL directly also updates the stored preference — an explicit link is an explicit choice.
- `t: SiteContent` — the full resolved dictionary for the active locale (`content/en.ts` or `content/pt.ts`).
- `/` (`app/page.tsx`) renders no content: `components/LocaleRedirect.tsx` picks a language — stored preference first, then `navigator.languages`, then English — and replaces the URL. It is marked `noindex` and canonicalized to `/en` so it doesn't compete with the real pages, and it shows plain `/en` and `/pt` links for visitors without JavaScript.
- One wrinkle: `app/layout.tsx` is shared by both locales, so the prerendered HTML always says `lang="en"`. The provider corrects `document.documentElement.lang` on mount. The hreflang tags, which are what search engines actually read, are per-locale and correct in the static HTML. See BACKLOG.md for why the layout isn't moved inside `[locale]`.

## SEO and social preview

- `lib/site.ts` holds `SITE_URL`, read from `NEXT_PUBLIC_SITE_URL` at build time with a placeholder fallback. Canonical URLs, hreflang alternates, Open Graph URLs and the sitemap are all derived from it, so pointing the site at a real domain is a one-variable change.
- Each locale page emits: `<link rel="canonical">`, one `<link rel="alternate" hreflang>` per locale plus `x-default`, Open Graph and Twitter card tags, and a schema.org `Person` JSON-LD block (name, job title, location, languages, topics, GitHub/LinkedIn as `sameAs`).
- The 1200×630 preview cards are committed PNGs (`public/og-en.png`, `public/og-pt.png`) generated by `scripts/render-og.mjs` (`npm run og`). Next's `opengraph-image` route convention would be the idiomatic choice, but its bundled `@vercel/og` resolves its font and wasm files with `path.join(import.meta.url, ...)`, which produces an invalid file URL on Windows and fails the export — the script renders the same design through a patched copy of that bundle.

## Analytics

`components/Analytics.tsx` renders a single `<Script>` and only when `NEXT_PUBLIC_ANALYTICS_SRC` is set at build time; otherwise it returns `null` and the site makes no third-party requests at all. It passes both Umami's `data-website-id` and Plausible's `data-domain`, and each script ignores the attribute it doesn't know, so switching providers is a change of environment variables rather than of code.

Every section component is a client component (`'use client'`) that calls `useLocale()` and reads its copy from `t`. There is no per-key translation function (`t('foo.bar')`) — instead each locale file is a fully-typed `SiteContent` object (see `lib/types.ts`), so a missing translation is a TypeScript compile error, not a silent runtime fallback.

Project descriptions are the one exception: `content/projects.ts` keeps `description: { en, pt }` inline per project, since project data (language, topics, stars) is locale-independent and only the description needs both languages.

## Content flow

```
content/en.ts, content/pt.ts   -> SiteContent (resume-derived copy)
content/projects.ts            -> ProjectData[] (GitHub-derived copy, locale-independent fields + bilingual description)
components/*                   -> pure presentation, no data fetching, no hardcoded copy
```

Nothing is fetched at runtime or at build time from the GitHub API — repo metadata (language, topics, stars, homepage) was captured manually into `content/projects.ts` and should be refreshed by hand when it goes stale (see CONTENT_GUIDE.md).

Project card thumbnails are GitHub's auto-generated Open Graph images, derived in `ProjectCard.tsx` from `project.githubUrl` (`github.com/x/y` → `opengraph.githubassets.com/1/x/y`) rather than stored as a field — no extra data to keep in sync, and the image updates itself if the repo's description/stars change.

## Styling

Tailwind CSS utility classes only, no component library. Palette is theme-aware via CSS variables (see Theme section above): dark by default (near-black `#0a0a0a` background, near-white `#f5f5f5` text), with a light theme (`#fff`/`#111`) available via the toggle. A single blue accent (lighter in dark mode for contrast) is reserved for links. Layout is constrained to a `max-w-content` (760px) column, mirroring the reference site's single-column, generous-whitespace look.

## Static export

`next.config.js` sets `output: 'export'` and `images.unoptimized: true` so `npm run build` produces a fully static `out/` directory with no Node server required — deployable to GitHub Pages, Vercel, Netlify, S3, etc. No deploy workflow is configured yet (hosting target undecided — see BACKLOG.md).
